## Motivation

Plans 001–005 established the object-only styling runtime, reactive provider
configuration, component migration, and v4-only consumer integration. Review
of the post-migration implementation found two P1 composition regressions:

1. `Select` and `MultiSelect` reconstruct provider and instance class/style
   layers with local spreads instead of routing all precedence through
   `resolveComponentStyle()`.
2. `Dialog` and `Sheet` pass their resolved overlay slot class to
   `Modal.Content` as an explicit primitive override, which erases Modal's
   structural overlay behavior whenever an overlay slot is customized.

This plan fixes those boundaries and updates the repository's plans, tests,
TODOs, README, and fixture terminology so they describe the implementation
that actually exists.

## Steps

### Step 1: Synchronize and inspect the existing implementation

Fetch and fast-forward `origin/style-refactor`, verify the branch and current
commit, and inspect `resolveComponentStyle()`, both Select wrappers,
`BaseSelect`, Modal, Dialog, Sheet, their tests, consumer helpers, and planning
files. Preserve any pre-existing user changes and stop if the branch cannot be
updated safely.

### Step 2: Restore Select and MultiSelect resolver ownership

Create one wrapper-level `resolveComponentStyle()` call in each of Select and
MultiSelect with reactive provider and instance getters. Pass:

- `resolved.rootClass()` and `resolved.rootStyle()` through the BaseSelect
  `class`/`style` channel;
- only a reactive named-slot dictionary through BaseSelect `classes`/`styles`;
- the same resolved named-slot accessors to default option renderers.

Do not pass a pre-resolved `root` entry through both channels. Keep the existing
control-specific resolver as the source of truth for control, input, leading,
trigger, clear, and MultiSelect tag slots. Do not introduce another generic
style-merging algorithm or snapshot provider/instance objects outside
accessors.

### Step 3: Add Select and MultiSelect regressions

Use `MoraineProvider` and real conflicting atomic utilities to verify for both
public wrappers:

- provider root classes are weaker than instance `classes.root`, while
  unrelated classes survive;
- instance `class` is strongest on the root;
- root styles merge by property and `instance.style` is strongest;
- named-slot classes are merged with `cn()` and instance conflicts win;
- named-slot styles merge by property and instance conflicts win;
- replacing provider and instance class/style objects updates an existing
  mounted root without remounting it.

### Step 4: Preserve Dialog/Sheet overlay composition

Keep `Modal.Content overlayClass` as a complete primitive-level takeover.
At the Dialog and Sheet composition boundary, merge
`MODAL_OVERLAY_CLASS` with the resolved overlay slot using `cn()` before
passing it to Modal. Do not duplicate the canonical class string, move
provider ownership into Modal, or alter Dialog/Sheet content takeover
semantics.

### Step 5: Add overlay ownership regressions

Assert that custom and provider Dialog/Sheet overlay slots retain representative
Modal behavior (`fixed`, `inset-0`, `z-floating`, enter/exit animation classes,
and reduced-motion behavior) while allowing a conflicting visual utility to be
overridden through `cn()`.

Keep a direct Modal test proving that `overlayClass="custom-overlay"` does
not receive the default Modal overlay class implicitly.

### Step 6: Refresh fixture terminology and bookkeeping

Rename `PackedConsumer`/`createPackedConsumer`/`removePackedConsumer` and
descriptions to `IsolatedConsumer` and isolated built-dist terminology where
needed. Keep the built-dist copy and all CSS assertions unchanged.

Create and maintain the detailed Plan 005.5 record, insert it between Plans 005
and 006, make Plan 006 depend on it, refresh Plan 005 as completed historical
bookkeeping, refresh Plan 006's post-005 current state and manual package
validation wording, and update `execute_plan.md` first for this plan and then
for Plan 006 only after this plan is fully verified.

Mark Wind3 support complete in `todo.md`, retain the production barrel import
optimization TODO, and make README development commands match `package.json`.

### Step 7: Verify and close the plan

Run focused Select, overlay, and provider tests before the full gates. Run
type checks, isolated consumer integration, build artifact assertions, docs
build, stale-terminology review, and the full QA/test gate. Inspect formatter
changes and `git diff --check`. Only after every required check passes, mark
this plan `DONE`, update its row in `plans/README.md`, and rewrite
`execute_plan.md` as the entry point for Plan 006.
