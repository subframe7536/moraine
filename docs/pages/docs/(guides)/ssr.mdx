Moraine supports SolidJS server rendering and hydration. Your application must still render the
same initial state on the server and client, defer browser-only work, and create conditional JSX
only when its branch renders.

This guide covers IDs, portals, content ownership, responsive state, and locale.

## Deterministic Hydration IDs

Accessible components need matching IDs between elements, for example a trigger's `aria-controls` and a content panel's `id`. Random IDs differ between server and client and cause hydration mismatches.

Use `createId` from `moraine/utils` to generate IDs that match across server rendering and client hydration. It builds on Solid's `createUniqueId`. Pass an accessor as the first argument to prefer a caller-provided ID, and a prefix as the second:

```tsx
import { createId } from 'moraine/utils'

function CustomField() {
  const id = createId() // Returns an accessor with the same ID on the server and the client

  return (
    <div>
      <label for={id()}>Username</label>
      <input id={id()} type="text" />
    </div>
  )
}
```

## Hydration-Safe Portals

Overlays such as `Dialog`, `Sheet`, `Drawer`, `Popover`, `Tooltip`, `DropdownMenu`, and `ContextMenu` render their content through a Solid `<Portal>`. The portal mounts into the `body` of the trigger's document, or into the `mount` element when you set one.

In Moraine:

- Overlays default to closed, so the server output contains only the trigger.
- Portals emit no server markup, so overlay content renders only on the client, even when an overlay starts open. The server and initial client trees match.
- Read browser APIs in `onSettled`, the side-effect phase of `createEffect`, or event handlers. For
  browser-only content, keep the server and initial client tree identical, then reveal that content
  after hydration.

```tsx
import { Button, Dialog } from 'moraine'

export function UserDialog() {
  return (
    <Dialog>
      <Dialog.Trigger as={Button}>Edit Profile</Dialog.Trigger>
      {/* Content portals to the body on the client only, so hydration matches */}
      <Dialog.Content title="Edit Profile">
        <p>Update your profile details below.</p>
      </Dialog.Content>
    </Dialog>
  )
}
```

## Conditional JSX and item content

Create JSX inside the branch that renders it. For collection items with optional panels, pass
`content` as a component so an inactive panel is not built, and does not consume hydration IDs,
before it mounts:

```tsx
import { Tabs } from 'moraine'

export function SettingsTabs() {
  return (
    <Tabs
      items={[
        { value: 'account', label: 'Account', content: () => <p>Account settings</p> },
        {
          value: 'notifications',
          label: 'Notifications',
          content: () => <p>Notification settings</p>,
        },
      ]}
    />
  )
}
```

The same rule applies to JSX panel data in [Accordion](/components/accordion) and
[Stepper](/components/stepper). Keep server and client item order and initial selection equal.

## Render-function children

Several props accept either JSX or a render function `(props) => JSX.Element`:

- `children` of [Button](/components/button), [ToggleButton](/components/toggle-button), [CopyButton](/components/copy-button), and [Slider](/components/slider)
- Trigger and item `children` of [BaseSelect](/components/base-select)
- Content `children` of [Dialog](/components/dialog), [BaseDialog](/components/base-dialog), [Sheet](/components/sheet), and [Drawer](/components/drawer)
- Handle `children` of [Resizable](/components/resizable)

For these props, **declare the function parameter** even when your callback does not read it:

- A zero-argument function `() => JSX.Element` is called as a plain reactive accessor without a component boundary.
- A function that declares its parameter `(state) => JSX.Element` is mounted as a component with its own Solid owner and lifecycle.

By contrast, [Field](/components/field) `children` and [HoverCard](/components/hover-card) content invoke every function with their render props regardless of parameter count, inside a tracked scope.

## Responsive Queries in SSR

Browser APIs such as `window.matchMedia` do not exist on the server. A component that renders different layouts by screen width needs a deterministic server default.

Moraine's `createMediaQuery` takes a `defaultValue` (default `false`) that is the state during SSR and the first client render. It updates from `matchMedia` after mount:

```tsx
import { createMediaQuery } from 'moraine/utils'
import { Show } from 'solid-js'

export function Navigation() {
  // false on the server and during hydration; follows matchMedia after mount
  const isDesktop = createMediaQuery('(min-width: 1024px)', false)

  return (
    <nav>
      <Show when={isDesktop()} fallback={<MobileDrawer />}>
        <DesktopNav />
      </Show>
    </nav>
  )
}
```

## Transition Presence & Exit Lifecycles

Solid's `<Show>` unmounts elements as soon as its condition becomes false. Moraine components use `createTransitionPresence` internally to keep exiting overlays mounted while CSS exit animations run.

During server rendering:

- Hidden or transitioning elements keep deterministic closed states.
- Animation variables such as `--mo-collapsible-content-height` start at safe initial values (`0px`) without DOM measurement.

## Locale and Direction

SSR and the first client render use `en-US`; a root `MoraineProvider` follows `navigator.language` only after hydration. To render localized text on the server, pass `locale` from a cookie or an `Accept-Language` header, and set `lang` and `dir` on `<html>`. See the [Localization guide](/docs/localization).

## Best Practices for SSR Safety

1. **Avoid `window` or `document` in the component body**: Read window dimensions, `localStorage`, or DOM properties inside `onSettled`, the side-effect phase of `createEffect`, or user event handlers (`onClick`, `onInput`), never while the component or the compute phase runs.
2. **Deterministic initial state**: Initialize controlled signals with static defaults that the server evaluates the same way as the client.
3. **Use Moraine primitives for overlays**: Built-in primitives already manage portals, scroll locks, and focus containment, so you do not need custom SSR guards.
