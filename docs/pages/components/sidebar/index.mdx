Trigger can appear anywhere inside the root, and `Sidebar.Rail` sits directly between `Panel` and `Inset`. On mobile, `Sidebar.Panel` renders its regions inside an internal Drawer. `Sidebar.Inset` renders a `<main>` landmark by default, so keep page content inside it rather than adding another `<main>`.

## Usage

Use Sidebar for application-shell navigation that stays inline on desktop and moves into a
mobile drawer. Use [Drawer](/components/drawer) for a standalone gesture-enabled drawer that is not a persistent
layout region. Use [NavigationMenu](/components/navigation-menu) for a website header of links and
panels.

`Sidebar` is both the state provider and desktop layout root. `Sidebar.Panel` renders
inline on desktop and moves the same content into a mobile Drawer on smaller viewports.

```tsx
import { Sidebar } from 'moraine'

export function Example() {
  return (
    <Sidebar>
      <Sidebar.Panel>
        <Sidebar.Content>
          <Sidebar.Group>
            <Sidebar.GroupLabel>Navigation</Sidebar.GroupLabel>
            <Sidebar.Menu>
              <Sidebar.MenuItem>
                <Sidebar.MenuButton leading="i-lucide:home" isActive>
                  Home
                </Sidebar.MenuButton>
              </Sidebar.MenuItem>
              <Sidebar.MenuItem>
                <Sidebar.MenuButton leading="i-lucide:settings">Settings</Sidebar.MenuButton>
              </Sidebar.MenuItem>
            </Sidebar.Menu>
          </Sidebar.Group>
        </Sidebar.Content>
      </Sidebar.Panel>
      <Sidebar.Inset>Content</Sidebar.Inset>
    </Sidebar>
  )
}
```

### Responsive navigation ownership

Keep one navigation tree inside `Sidebar.Panel`. Put the application header outside the
frame, then place `Sidebar.Trigger` where users need to reveal or collapse navigation. If a
child needs to coordinate with the sidebar, read `Sidebar.useContext()` within the provider rather
than maintaining a second open state.

```tsx
<Sidebar.Trigger as={Button} variant="ghost" size="icon-sm" aria-label="Toggle sidebar">
  Open
</Sidebar.Trigger>
```

Root `open`, `defaultOpen`, and `onOpenChange` drive whichever layout is active: the desktop panel or
the mobile drawer. Uncontrolled desktop and mobile states are remembered separately. `defaultOpen`
seeds both layouts, `defaultOpen="desktop-only"` seeds only the panel, and when omitted the desktop
panel starts expanded and the drawer starts closed. Switching
layouts never calls `onOpenChange` and never writes a controlled `open`. Leaving mobile closes an
uncontrolled drawer, and returning to desktop restores the desktop state. The trigger, the rail, and
Escape or overlay dismissal of the drawer all report through `onOpenChange`.
Menu buttons with `href` close the mobile drawer on activate; set `closeOnSelect={false}` on a
button to keep it open. When `isMobile` is omitted, `breakpoint` (default `768`) drives
`(max-width: ${breakpoint}px)` via `matchMedia`. Pass `isMobile` to force either layout.

Root `classes` and `styles` set defaults for the panel, region, group, menu, menu item, and sub-menu slots.
On mobile, the sidebar renders inside a Drawer. Style the Sidebar regions through their own
slots; Sidebar overrides do not style the internal Drawer. See [Theming](/docs/theming) for
nested Provider behavior.

`Sidebar` declares `--mo-sidebar-width` on its root. Pass a numeric `width` (controlled),
`defaultWidth` (uncontrolled), `minWidth` (default `224`), or `maxWidth` (default `480`) in pixels;
when none is given the recipe fallback `var(--sidebar-width, clamp(14rem, 25%, 20rem))` applies, so
you can also set the global `--sidebar-width` in CSS or with `presetMoraine`. When collapsed, the
desktop panel keeps its width and slides out with a negative margin, so its content does not reflow
during the transition.

The root uses `h-full` so it can sit inside a bounded container. For a viewport shell, pass
`class="h-dvh"` (or `h-svh`) on the root.

Call `Sidebar.useContext()` from a descendant for `isMobile`, `isOpen`, `state`, `setOpen`, and
`toggle`. A global application header belongs outside the frame.

### Resizable rail

Place `Sidebar.Rail` directly between `Sidebar.Panel` and `Sidebar.Inset` to make the desktop
sidebar resizable; it renders nothing on mobile. Dragging the rail updates the pixel width live
between `minWidth` and `maxWidth`; releasing emits `onWidthCommit` once. A click without movement
toggles the sidebar, and dragging below half of `minWidth` closes it — drag back to reopen.
Because the root is a splitter scope, a nested `Resizable` inside `Sidebar.Inset` whose handle has
`intersection` and touches the rail cross-drags both.

| Key                                                          | Action                                            |
| ------------------------------------------------------------ | ------------------------------------------------- |
| Growth arrow (`ArrowRight` or `ArrowLeft`, follows geometry) | resize by 16px                                    |
| Growth arrow + `Shift`                                       | resize by 1px                                     |
| Opposite arrow                                               | shrink (clamps at `minWidth`, never closes)       |
| `Home` / `End`                                               | `minWidth` / `maxWidth`                           |
| `Enter`                                                      | toggle open (the only key that acts while closed) |

To persist desktop layout across reloads, control `open` and `width` from the app and store them in
a cookie (not `localStorage`, which mismatches SSR hydration) inside `onOpenChange` and
`onWidthCommit`.

### Navigation menu

Build labeled navigation with these parts:

- `Sidebar.Group`: section container that holds a label and a menu
- `Sidebar.GroupLabel`: section title; set `as="h2"` or another tag when the page needs a heading
- `Sidebar.Menu`: `<ul>` list of the items of a group
- `Sidebar.MenuItem`: `<li>` that holds one `MenuButton` with an optional `MenuAction`, or a
  `MenuSub`
- `Sidebar.MenuButton`: polymorphic button (`button`, `a`, or a custom link) with `leading`,
  `trailing`, and `isActive`. It owns the hover, active, focus, and disabled styles. `leading` and
  `trailing` accept icon names
- `Sidebar.MenuAction`: controls placed over the end of the item's first row, such as a dropdown
  menu trigger. The button stays highlighted while the pointer is over the action. The button does
  not reserve space for the action, so add `pe-8` to a `MenuButton` whose label can run under it
- `Sidebar.MenuSub` / `MenuSubTrigger` / `MenuSubContent`: collapsible sub-navigation on
  `Collapsible`, placed inside a `MenuItem`. `MenuSubTrigger` renders a `MenuButton` with a
  chevron that rotates while expanded. `MenuSubContent` renders a nested `<ul>` of `MenuItem`s

```tsx
<Sidebar.Group>
  <Sidebar.GroupLabel>Architecture</Sidebar.GroupLabel>
  <Sidebar.Menu>
    <Sidebar.MenuItem>
      <Sidebar.MenuSub defaultOpen>
        <Sidebar.MenuSubTrigger leading="i-lucide:route">Routing</Sidebar.MenuSubTrigger>
        <Sidebar.MenuSubContent>
          <Sidebar.MenuItem>
            <Sidebar.MenuButton href="/layouts">Pages and Layouts</Sidebar.MenuButton>
          </Sidebar.MenuItem>
        </Sidebar.MenuSubContent>
      </Sidebar.MenuSub>
    </Sidebar.MenuItem>
  </Sidebar.Menu>
</Sidebar.Group>
```

Use [DropdownMenu](/components/dropdown-menu) inside header, footer, or `Sidebar.MenuAction` for workspace
switchers and row actions. Those menus are actions, not the sidebar's navigation tree.
