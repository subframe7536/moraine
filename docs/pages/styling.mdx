Each component includes a built-in recipe: its default slot classes, variants, and variant defaults. Moraine uses atomic utility classes for those styles. Configure your CSS engine to scan the published classes and load Moraine's theme integration; the package does not include precompiled component CSS.

## UnoCSS

Use either the Wind4 or Wind3 preset with `presetMoraine()`, and include Moraine's published JavaScript in the content scan.

```ts title="unocss.config.ts (Wind4)" {1,5} group-id="unocss"
import { defineConfig, presetWind4 } from '@subf/unocss'
import { presetMoraine } from 'moraine/unocss'

export default defineConfig({
  presets: [presetWind4(), presetMoraine()],
  content: {
    filesystem: ['./node_modules/moraine/dist/**/*.{mjs,jsx}'],
  },
})
```

```ts title="unocss.config.ts (Wind3)" {1,5} group-id="unocss"
import { defineConfig, presetWind3 } from '@subf/unocss'
import { presetMoraine } from 'moraine/unocss'

export default defineConfig({
  presets: [presetWind3(), presetMoraine()],
  content: {
    filesystem: ['./node_modules/moraine/dist/**/*.{mjs,jsx}'],
  },
})
```

The preset registers Moraine theme tokens, shared animations, semantic z-index values, and `data-*` / `aria-*` variants. `globalStyles` defaults to `true`.

### Color variables

The preset can generate light and dark semantic variables. Nothing is emitted unless `colorVariables` is configured; selectors default to `:root` and `.dark`.

```ts
presetMoraine({
  colorVariables: {
    light: {
      foreground: 'oklch(20% 0 0)',
      primary: {
        DEFAULT: 'oklch(55% 0.2 260)',
        foreground: 'white',
        hover: 8,
        active: ({ base, foreground }) => `color-mix(in oklch, ${base}, ${foreground} 16%)`,
      },
      border: 'oklch(90% 0 0)',
    },
    dark: {
      foreground: 'oklch(96% 0 0)',
      primary: {
        DEFAULT: 'oklch(70% 0.16 260)',
        foreground: 'oklch(18% 0 0)',
      },
      border: 'oklch(32% 0 0)',
    },
    hoverAdjustment: 6,
    activeAdjustment: 12,
  },
})
```

## Tailwind CSS v4

Register the plugin and scan the published distribution. The `@source` path is relative to the stylesheet containing it, so adjust the leading `..` for your project layout.

```css
@import 'tailwindcss';
@plugin 'moraine/tailwind';
@source '../node_modules/moraine/dist';
```

`@source "moraine"` is not valid: Tailwind requires a resolvable source path. The plugin provides the same colors, typography, radius, shadows, animations, z-index values, and state variants as the UnoCSS preset.

## CSS variables Moraine reads

Like [shadcn/ui's CSS-variable theming](https://ui.shadcn.com/docs/theming), Moraine's built-in classes use semantic names such as `bg-primary`, `text-foreground`, and `rounded-lg`. The UnoCSS preset and Tailwind plugin map those classes to CSS variables that your application defines. They do not provide a default color palette. Moraine reads the tokens listed below.

| Role              | CSS variables                               |
| ----------------- | ------------------------------------------- |
| Page              | `--background`, `--foreground`              |
| Primary           | `--primary`, `--primary-foreground`         |
| Secondary         | `--secondary`, `--secondary-foreground`     |
| Card              | `--card`, `--card-foreground`               |
| Popover           | `--popover`, `--popover-foreground`         |
| Muted             | `--muted`, `--muted-foreground`             |
| Accent            | `--accent`, `--accent-foreground`           |
| Destructive       | `--destructive`, `--destructive-foreground` |
| Borders and focus | `--border`, `--input`, `--ring`             |

The integrations also read `--radius` for the `rounded-*` scale; `--font-sans`, `--font-mono`, and `--font-serif` for fonts; and `--shadow`, `--shadow-2xs`, `--shadow-xs`, `--shadow-sm`, `--shadow-md`, `--shadow-lg`, `--shadow-xl`, and `--shadow-2xl` for shadows. `--sidebar-width` is optional and falls back to `clamp(14rem,25%,20rem)`.

Define the values in your application stylesheet and override them for dark mode or a subtree. For example, this sets only some of the tokens; add the others used by your components:

```css
:root {
  --background: oklch(100% 0 0);
  --foreground: oklch(20% 0 0);
  --primary: oklch(55% 0.2 260);
  --primary-foreground: white;
  --radius: 0.625rem;
}

.dark {
  --background: oklch(18% 0 0);
  --foreground: oklch(96% 0 0);
  --primary: oklch(70% 0.16 260);
  --primary-foreground: oklch(18% 0 0);
}
```

For the eight surface colors above, optional `--*-hover` and `--*-active` variables control interaction states. Each hover value falls back to its base; each active value falls back to hover, then base. The UnoCSS `colorVariables` option above can generate semantic **color** variables from supplied light and dark values; it does not supply radius, shadow, or font values. Component-specific measurement and animation variables such as `--mo-collapsible-content-height` and `--mo-anim-duration` serve different purposes.

## Icons

`moraine/icon.css` is an optional runtime mask asset. It is independent of component utility generation and does not replace the required Tailwind plugin or UnoCSS preset.

```css
@import 'moraine/icon.css';
```

You may instead configure an engine icon integration such as `@iconify/tailwind`. In either case, keep the Moraine plugin or preset and the published-distribution scan.

## Animation duration variables

```css
:root {
  --mo-anim-duration: 180ms;
  --mo-anim-duration-enter: 150ms;
  --mo-anim-duration-exit: 100ms;
  --mo-anim-duration-loop: 2s;
  --mo-anim-duration-spin: 1s;
}
```

The general variable overrides every Moraine CSS animation. The semantic variables target entry, exit, looping, and spinner animations separately. CSS transitions retain the duration and timing function configured by the host Tailwind CSS or UnoCSS setup.

## Interactive color tokens

Use the same semantic color tokens when styling your own interactive surfaces:

```tsx
<button class="bg-primary hover:bg-primary-hover active:bg-primary-active text-primary-foreground">
  Continue
</button>
```

## Override component styles

Where should you put a style override?

| Need                                          | Surface                        |
| --------------------------------------------- | ------------------------------ |
| Application or library defaults               | Theme                          |
| Defaults for one composite component instance | Root `classes` / `styles`      |
| Override slots rendered by a specific part    | Part `classes` / `styles`      |
| Override the part's primary DOM element       | `class` / `style` on that part |

For a Button, use `class` and `style` on the element itself. Use `classes` to change a named slot such as its label:

```tsx
<Button class="bg-red-500" style={{ borderColor: 'red' }} classes={{ label: 'text-white' }}>
  Continue
</Button>
```

For a Dialog, root `classes` and `styles` set defaults for that instance. Put native DOM attributes and direct overrides on the part that renders the element:

```tsx
<Dialog classes={{ content: 'max-w-lg', body: 'space-y-4' }}>
  <Dialog.Trigger class="font-semibold">Edit profile</Dialog.Trigger>
  <Dialog.Content title="Profile" class="shadow-xl">
    Profile settings
  </Dialog.Content>
</Dialog>
```

A part rendering one public slot uses `class` and `style`. A part rendering multiple configurable slots may also expose `classes` and `styles` for those slots. `Dialog.Trigger` uses direct overrides; `Dialog.Content` can configure its `overlay`, `content`, `header`, `title`, `description`, `contentClose`, `body`, and `footer` slots.

Roots that render an element, such as `InputGroup`, `Collapsible`, and `SidebarFrame`, also accept direct `class` and `style` for that root element. Headless roots such as `Dialog`, `Popover`, and `Tooltip` have no element for direct DOM props; use root `classes` and `styles` for instance defaults. Root-only components (`Icon`, `Kbd`, `Separator`, and the bound `form.Form`) expose direct `class` and `style`. Their Theme entries still have a `root` slot.

### Style slots and DOM slots

Use camelCase names in `classes` and `styles`; use the documented `data-slot` values in CSS selectors or DOM inspection. The rendered values use kebab-case: the component name for `root`, or the component name followed by the slot name for other slots. Recipes and Theme entries use the same camelCase style keys.

```tsx
<Select classes={{ itemLabel: 'font-semibold' }} />
// The label element renders with data-slot="select-item-label".
```

Some components expose style keys for elements rendered by a nested Moraine component. The [advanced style resolution](#advanced-style-resolution) section explains how their DOM slot names differ.

## Component kinds

The `Single` and `Composite` labels describe how you compose a component, regardless of how many DOM elements or style slots it renders.

**Single** components expose their configuration through one component's props. `Card` is single even though it has header, body, and footer slots. Apply root styles with `class` and `style`, and use `classes` and `styles` for named slots when the component supports them.

```tsx
<Card title="Account" class="max-w-md" classes={{ body: 'space-y-4' }}>
  Account settings
</Card>
```

**Composite** components expose attached parts that you arrange explicitly. `SidebarFrame` renders a layout root and accepts slot overrides, while each part also accepts its own `class` and `style`.

```tsx
<SidebarFrame class="h-80" classes={{ sidebar: 'bg-muted' }}>
  <SidebarFrame.Sidebar>
    <SidebarFrame.SidebarBody class="p-4">Navigation</SidebarFrame.SidebarBody>
  </SidebarFrame.Sidebar>
  <SidebarFrame.Main class="p-6">Workspace</SidebarFrame.Main>
</SidebarFrame>
```

The bound `form.Form` is single: `createForm()` returns separate `Form` and `Field` components. Each component's API lists its supported style overrides.

## Class merging configuration

Moraine uses the upstream [cn](https://github.com/shadcn-ui/cn) package for utility-class conflict resolution. `cnConfig` accepts its `ConfigExtension` options; Moraine adds semantic z-index and animation rules to the upstream defaults. `cn`, `createCn`, and `useCn` are exported from `moraine`:

| API                 | Rules and scope                                                                           |
| ------------------- | ----------------------------------------------------------------------------------------- |
| `cn(...classes)`    | Fixed upstream defaults plus Moraine's semantic z-index and animation rules.              |
| `createCn(config?)` | An independent merger with application rules, usable in modules, scripts, or server code. |
| `useCn()`           | A stable merger bound to the nearest Provider at component initialization.                |

Components use the nearest Provider's rules for recipe evaluation and final class merging. `cnConfig` accepts `extend`, `override`, `prefix`, and `cacheSize`. Rules apply in order: upstream defaults, Moraine extensions, application `override`, then application `extend`. `cn()` also combines conditional class values; it does not generate CSS or scan component files.

```ts title="app-cn.ts"
import { createCn } from 'moraine'
import type { CnConfig } from 'moraine'

export const appCnConfig = {
  extend: {
    classGroups: {
      density: ['density-roomy', 'density-compact'],
    },
  },
} satisfies CnConfig

export const appCn = createCn(appCnConfig)
```

Define the corresponding CSS in your application. Conflict rules do not generate CSS or expand UnoCSS shortcuts.

```css
.density-roomy {
  padding: 1rem;
}
.density-compact {
  padding: 0.5rem;
}
```

```tsx
import { Button, MoraineProvider, cn, useCn } from 'moraine'
import { appCnConfig } from './app-cn.ts'

function Preview() {
  const scopedCn = useCn()
  return (
    <>
      <div class={cn('density-roomy', 'density-compact')}>Both classes remain</div>
      <div class={scopedCn('density-roomy', 'density-compact')}>Compact wins</div>
      <Button class="density-roomy density-compact">Compact button</Button>
    </>
  )
}

export function App() {
  return (
    <MoraineProvider cnConfig={appCnConfig}>
      <Preview />
      <MoraineProvider theme={null}>
        <Preview />
      </MoraineProvider>
      <MoraineProvider cnConfig={{}}>
        <Button class="density-roomy density-compact">Default merging</Button>
      </MoraineProvider>
    </MoraineProvider>
  )
}
```

| `cnConfig`             | Behavior                                                                                                             |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Omitted or `undefined` | Inherit the current parent merger, or use default rules at the root.                                                 |
| An extension object    | Replace the inherited merger with Moraine defaults plus this object; parent application extensions are not retained. |
| `{}`                   | Reset to Moraine default rules.                                                                                      |

Replace the config object to update existing descendants. Changing it back to `undefined` resumes live parent inheritance. Theme and class merging are independent: `theme={null}` clears inherited Theme overrides while preserving the current merger. `prefix` only changes class parsing; it does not prefix official theme classes or generated CSS. `cacheSize: 0` disables the upstream result cache.

Call `useCn()` during initialization in a descendant such as `Preview`; a parent cannot read a Provider that it will later return. The captured handle remains usable in events and after `await` while its owner lives. Calls in JSX or memos track config changes; a previously computed string does not update itself. Without a Provider, `useCn()` uses the same rules as `cn`.

A merger cannot restore classes already removed by another merger. Use `useCn()` in components or `appCn` in ordinary helpers when application code needs the same rules. Each part merges its own classes with its nearest Provider's rules; classes already resolved on the root keep the root's rules.

## Themes and Providers

Components use their built-in recipes by default. Add `MoraineProvider` only when you need Theme or `cnConfig` overrides.

| `theme`                | Behavior                                                                                                                   |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Omitted or `undefined` | Inherit the parent Theme overrides; at the root, use the built-in component recipes with no Theme overrides.               |
| A Theme object         | Use that Theme instead of inherited Theme overrides; built-in component recipes remain the base. Use `extends` to compose. |
| `theme={null}`         | Clear inherited Theme overrides and return to the built-in component recipes.                                              |

```tsx
import { Button, MoraineProvider } from 'moraine'
import { defineTheme } from 'moraine/theme'

const brand = defineTheme({
  button: { defaultVariants: { size: 'sm' }, base: { root: 'rounded-xl' } },
})
const section = defineTheme({
  extends: brand,
  button: { base: { root: 'shadow-md' } },
})

<MoraineProvider theme={brand}>
  <Button>Brand presentation</Button>
  <MoraineProvider theme={section}>
    <Button>Extended presentation</Button>
  </MoraineProvider>
  <MoraineProvider theme={null}>
    <Button class="my-button">Custom presentation</Button>
  </MoraineProvider>
</MoraineProvider>
```

`defineTheme()` creates an immutable Theme override; with no component entries, it adds no overrides to the built-in recipes. `extends` composes Theme override layers, preserving parent values where the child supplies `undefined`, and evaluates parent overrides before child overrides. Update presentation by replacing the Theme object. Setting `theme` back to `undefined` resumes inheritance and follows subsequent parent updates.

### Recipes and defaults

Component configurations accept `base`, `variants`, `compoundVariants`, and `defaultVariants`. Each contribution maps slot names to classes and full `--` custom property names to root CSS variables.

```ts
const theme = defineTheme({
  button: {
    defaultVariants: { size: 'sm' },
    variants: { size: { sm: { label: 'tracking-wide' } } },
    compoundVariants: [{ variants: { size: 'sm', variant: 'outline' }, root: 'border-2' }],
  },
})
```

Visual values resolve from explicit instance props, inherited composition/Field values, and finally the latest Theme default. Only `undefined` falls back. `null` suppresses the default and selects no branch; `false`, `0`, and `''` remain explicit values where the Variant type supports them. Every recipe for a component uses the same final visual values.

Component recipes are readonly advanced exports from `moraine/styles`. Theme customization uses `defineTheme()`; recipe construction and merge builders are internal Moraine implementation details.

### State selectors

Recipe Variants describe stable component options that select class branches, including visual treatments and configured layout or interaction modes. Transient disabled, required, selected, open/closed, loading, orientation, and placement state use the component's documented data/ARIA attributes. Keep state selectors flat so both CSS engines can scan them:

```ts
const theme = defineTheme({
  button: { base: { root: 'data-disabled:opacity-50 data-loading:cursor-wait' } },
  select: { base: { control: 'focus-within:ring-2' } },
  popover: { base: { content: 'data-[side=bottom]:mt-2' } },
})
```

Measurements such as slider percentages and floating transform origins remain inline styles or CSS variables.

### Theme CSS variables

Each recipe branch can mix slot classes and root CSS variables in one flat object. Declare full custom property names so declarations and class references use the same spelling.

```tsx
const theme = defineTheme({
  slider: {
    variants: {
      size: {
        lg: { '--s-size': '8px' },
      },
    },
    compoundVariants: [
      {
        variants: { size: 'lg', variant: 'bold' },
        track: 'rounded-lg',
        '--s-size': '32px',
        '--s-len': '20px',
      },
    ],
  },
})
```

Classes and variables resolve together in base, selected variant, then matching compound order. Later non-null variable values override earlier values; numbers are passed through without units. Parent and child recipes receive the same resolved variants, with child variables overriding parent variables by property.

Recipe and Theme CSS variables are applied first, followed by inherited styles, instance `styles[rootSlot]`, and the instance root `style`. Changing variants or removing Theme overrides clears variables that no longer apply.

### Advanced style resolution

Classes reach the active Moraine `cn` merger in this order: built-in recipe, nearest Provider Theme, composite-root instance defaults, part slot overrides, then direct `class` on the part's primary slot. A later class does not always replace an earlier one: conflict resolution depends on `cnConfig`, and unknown or non-conflicting classes can coexist. Recipe merge boundaries also matter. Inline style properties use overwrite precedence in the same order: recipe or Theme CSS variables, root `styles[slot]`, part `styles[slot]`, then direct primary `style`.

Each rendered composite part resolves its recipe with its nearest `MoraineProvider`, including parts rendered through a Portal. Defaults from the nearest matching component root still reach that part, while a Provider inside the root supplies the part's Theme and `cnConfig`. A nested instance of the same component starts with its own overrides instead of inheriting those of the outer instance. Theme overrides and instance overrides both contribute to the resolution above; a Theme object replaces inherited Theme overrides unless explicitly composed with `extends`.

CSS variables target individual slots. Portaled DOM does not inherit variables from a trigger or layout root, so apply a variable to each affected slot, for example `styles={{ content: { '--x': '...' }, overlay: { '--y': '...' } }}`. Moraine does not copy root variables to other slots. Empty overrides do not disable built-in recipes; there is no unstyled or replacement mode.

Nested Moraine components may render nodes with their own DOM slot names. Pagination's page Button root renders as `pagination-item`, but its label remains `button-label`. The `classes` and `styles` APIs of `AvatarGroup`, `CheckboxGroup`, and `Pagination` can also target child internals: `AvatarGroup.classes.image` targets `avatar-image`, `CheckboxGroup.classes.icon` targets `checkbox-icon`, and `Pagination.classes.controlLabel` targets `button-label`. AvatarGroup's fallback content key is `fallbackContent`.

### Reactive replacement and native refs

Changing a Provider's `theme` updates classes without remounting component DOM. Input and Textarea keep their values, focus, selection, and refs. Their `ref` targets the editable native control. Use `InputGroup` for a shared wrapper and its ref.
